# translate.js browser regression tests

These tests run both checked-out release files, `translate.js/translate.js` and
`translate.js/translate.min.js`, separately in headless Chromium. Each file runs
the same complete set of scenarios.
Local pages and mocked `translate.json` / `language.json` responses make the
checks independent of external translation providers. They test browser behavior,
not translation quality or provider availability.

## Setup

Use Node.js 20 or newer. The test dependency is pinned in `package-lock.json`.

```bash
cd dev/e2e
npm ci
npx playwright install chromium
```

On Linux CI, use `npx playwright install --with-deps chromium` to install the
browser's operating-system dependencies too.

## Run

On Windows, double-click `translate.js/test.bat` from this checkout. It prepares
missing test dependencies, selects a usable headless Chromium (or downloads one
if necessary), runs the tests and keeps the result window open. It requires
Node.js 20 or newer; the first setup may need an internet connection. The launcher
prints both exact file paths and reports normal passes, known failures, skips
and unexpected failures for each file, followed by totals. A cached browser that
differs from the pinned version is identified in the output.

The launcher reads the files exactly as they exist in this checkout. It does not
regenerate `translate.min.js`. After changing the source, regenerate the minified
file through the project's release process before checking the updated release
pair. Passing the old minified file does not prove that it includes a source change.

The comments at the top of `translate.js/test.bat` contain the Windows environment
checklist and Node.js installation commands for people or AI assistants setting
up a fresh checkout. Node.js and npm must be installed first; the launcher does
not install or upgrade the system Node.js runtime itself.

For scripts that should not wait for a key press, use `test.bat --no-pause`.
The batch file preserves the test command's exit code.

To run from a terminal after setup:

```bash
npm test
```

From the repository root, the equivalent command is `npm run test:e2e`.
Both commands run the `chromium` source project and the `chromium-minified`
minified-file project. A failure in either project makes the command fail; an
unexpected failure in the first does not stop the second project from running.
The runner starts and stops fixture servers on `127.0.0.1:8123` and
`127.0.0.1:8124`; both ports must be free. It runs one worker with no retries.

Unexpected assertion failures and runtime errors return a nonzero exit code.
For each known limitation, the test checks the observed failure signature before
classifying a failed assertion as expected. A different error or failed setup
still fails the command. Once the assertion passes, the test passes normally
without changing its known-failure check.

Playwright includes expected failures in its successful-run total. Rows marked
`x` still reproduce a known problem; they do not mean that the problem is fixed.
The JSON report distinguishes them with `expectedStatus: "failed"`.

To run the known limitations as ordinary assertions as well:

```bash
npm run test:strict
```

Strict mode is expected to fail while the documented limitations remain. A
missing optional cache-clearing API is skipped in both modes; absence of a new
feature is not a runtime regression. Strict mode also tests both files, using
the `strict` and `strict-minified` projects. On Windows, the equivalent launcher
command is `translate.js/test.bat --no-pause --strict` from the repository root.

For focused development, forward Playwright options, for example:

```bash
npm test -- --grep "cache"
```

JSON results are written to `report/results.json`. Failure screenshots and traces
are written under `test-results/`, identified by project so the two builds can be
distinguished; these generated files are ignored by Git.
The committed screenshots and `report/test-output-after-fixes.txt` are historical
evidence from the original contribution and are not regenerated by this runner.

For an existing compatible Chromium installation, the optional environment
variable `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` selects its executable. Normal
development and CI should use the browser installed by the pinned Playwright
version for reproducible results.

## Coverage

- Static translation, selector rendering, ignore rules and translated attributes
- Opt-in translation of `input.value`
- Dynamic `childList` and `characterData` updates
- Language switching without reload and switching back
- Correct translated content after cache reuse, with no translation request
- Storage quota exhaustion and unavailable storage operations
- Iframe discovery, loading, navigation, nesting and configuration inheritance
- Cross-origin message compatibility and explicit origin allowlist behavior
- Initial and dynamically inserted Shadow DOM content
- Removal of `hash_*` localStorage entries and preservation of unrelated values,
  when the proposed `translate.storage.clearCache()` API exists

See [REPORT.md](REPORT.md) for the existing runtime limitations. Browser tests
cover these scenarios only; they do not establish that every browser, page or
translation provider works.

## Iframe regression matrix

`iframe.spec.js` adds 24 scenarios using the pages in `iframe-fixtures.js`.
The fixture server and Playwright config include them in the normal `test.bat`
run, for both release files. Every scenario verifies the SHA256 of each loaded
library response against the selected file on disk and checks browser errors.

Coverage includes static and dynamic frames, `about:blank`, `srcdoc`, siblings,
preloaded libraries, repeated scans, navigation, reload, removal/recreation,
dynamic content, language switches, multiple nesting levels, different ancestor
configuration, cross-origin boundaries and sandboxed frames. Navigation checks
include a same-origin URL that redirects cross-origin and a frame that returns
to the same origin after visiting another origin. Negative cases
exercise discovery rather than relying on a frame never being scanned.

To run the iframe assertions without known-failure exceptions on Windows:

```bat
translate.js\test.bat --no-pause --strict --grep iframe
```

The strict command deliberately fails when a covered existing defect is present.
See [IFRAME_REPORT.md](IFRAME_REPORT.md) for the baseline, exact known failure
conditions and the distinction between the configuration-source fix and other
iframe limitations. The matrix covers these cases in Chromium; it cannot prove
all possible iframe combinations or browser implementations.
