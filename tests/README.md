# translate.js 自动化测试

本目录集中保存 translate.js 的测试入口、按方法组织的测试模块、完整流程测试及测试工具。
目标是让开发者修改代码后运行同一个入口，及时发现参数处理错误、功能回退和浏览器异常。
测试应逐步覆盖每个方法的正常行为、边界、异常和相关参数组合；不能以少量正常示例代替详细验证。

## 已确定的目录和命名

```text
tests/
├─ README.md                       本文：目标、组织方式、待商定事项和进度
├─ COVERAGE.md                     逐方法参数与验证结果、已发现问题和待确认边界
├─ test-translate.js.bat            Windows 双击运行入口
├─ start.js                        准备依赖、选择浏览器、运行和汇总结果
├─ playwright.config.js            测试发现与浏览器配置
├─ method-inventory.js             从源码语法树清点入口，缺失模块时返回失败
├─ package.json / package-lock.json 锁定测试依赖
├─ modules/                        按方法命名，文件平铺，不建立多层方法子目录
│  ├─ storage.get.js                对应 translate.storage.get()
│  ├─ storage.set.js                对应 translate.storage.set()
│  ├─ storage.browser.memory.get.js 对应 translate.storage.browser.memory.get()
│  ├─ util.textReplace.js           对应 translate.util.textReplace()
│  └─ ...                           其余方法按相同规则各自保存独立用例
├─ scenarios/                      暂存现有跨方法的浏览器流程测试
├─ fixtures/                       本地测试页面及模拟接口服务
├─ helpers/                        多个测试确实需要时才提取公共辅助代码
├─ report/                         当前结果及保留的历史验证资料
└─ test-results/                   自动生成的失败截图、跟踪等文件
```

- 方法文件名省略共同的 `translate.` 前缀，其余路径与源码方法一致，例如 `element.iframe.execute.js`。
- `modules/` 保持平铺；不再按 `storage/browser/memory/` 等路径建立层层子目录。
- 一个方法对应一个测试模块文件；每种参数组合、边界或异常情况是独立测试，能够单独定位失败。
- 在一个方法文件内使用用例数组，每个元素生成一个独立测试；两种元素格式见下文。
- 不把不同参数组合藏在同一个循环或 `every` 中；每个组合分别登记。验证同一次结果、唯一性或连续状态变化时可以在一项内检查多个相关值。
- 多方法协作的完整流程放在 `scenarios/`，保留对真实页面最终行为的验证。
- 测试入口只发现 `modules/` 和 `scenarios/` 的 `.js` 文件；辅助程序和模拟服务不作为测试执行。
- 暂不为了统一外观拆分原有聚合场景；按已确认的用例格式逐步迁移和核对。

## 单个方法测试需要记录的内容

以下是覆盖要求；具体用例格式见下文。

1. 文件名对应被测方法，`remark` 说明每项要验证的行为；失败时能定位具体文件及用例。
2. 覆盖正常值、可选参数省略、边界值、特殊字符、适用的数据类型及相关参数间的组合。
3. 根据方法约定检查错误类型、返回值和副作用，例如是否修改输入数组、DOM、存储或内部状态。
4. 需要时验证连续调用、状态变化前后、失败后的行为以及功能之间的协作。
5. 预期结果来自明确的功能约定或独立核对，不能照着当前实现计算答案，再证明实现与自己一致。
6. 未定义的输入行为先记录并与维护者确认，不能自行规定必须成功、必须返回空值或必须抛错。
7. 每项独立报告结果，测试之间不依赖上一项留下的状态。

输入集合可能无限，有限测试不能证明任意输入下绝对没有 bug。为避免漏项，需要维护可核对的覆盖清单，
逐项记录方法、参数、已覆盖情况、待补充情况和待确认的行为。不能把“测试通过”写成“全部方法已覆盖”。

## 已确认的用例格式

文件名已经对应方法，无须在文件头再次声明被测方法；不要求手工填写 `id`，说明字段统一为 `remark`。
每个用例只使用下面两种格式之一。

普通用例填写 `remark`、`args`、`expected`。例如 `util.textReplace.js` 中的一个元素：

```js
{
  remark: '替换后方的全角逗号转为半角，并补上空格',
  args: ['你好，世界', '你好', 'Hello', 'english'],
  expected: 'Hello, 世界'
}
```

- `args` 按真实调用顺序保存参数，省略参数与显式传入 `undefined` 分开测试。
- `expected` 是预期返回值，不使用 `return` 作为字段名。严格比较实际返回值和预期值，数组及对象比较完整结构。
- `false`、`0`、空字符串、`null`、`undefined` 都可以是预期值；不能根据值的真假判断是否填写了 `expected`。

需要自行判断时，填写 `remark`、`test`。例如 `nomenclature.dispose.js` 中的一个元素：

```js
{
  remark: '传入字符串后，返回对象中的替换结果应正确',
  test: function () {
    const result = translate.nomenclature.dispose(
      '你好我好她也好', '好', 'hao', null
    );
    return result.resultText[0] === '你hao我hao她也hao';
  }
}
```

- `test` 自行完成调用及判断，无须再填写 `args` 和 `expected`。
- 最终结果严格等于布尔值 `true` 才通过；`false`、其他类型、漏写返回值、抛错和超时均失败。异步函数等待完成后按同一规则判断。
- 只要求自动检测是否通过；不要求返回错误详情对象，也不增加专门的诊断字段。失败后根据对应文件和备注分析原因。
- 沿用当前浏览器测试环境，函数内可直接使用 `translate`、`document`；所需数据在内部准备，不直接引用测试模块外层的 Node.js 变量。

两种格式的每个元素都独立执行，分别检查源码和压缩版。报告使用文件名、自动序号和 `remark` 区分用例，无须手工维护编号，也不要求备注唯一。
模块通过以下形式登记，不能使用两种格式之外的字段；旧 `id/name` 或拼错的字段会直接报错：

```js
'use strict';

require('../helpers/module')(__filename, [
  { remark: '空字符串的哈希为零', args: [''], expected: 0 }
]);
```

以上是 `util.hash.js` 的完整文件形式示例；实际文件应继续登记该方法的其他输入和边界。
普通调用根据文件名找到方法，并保留所属对象作为 `this`；需要 DOM、回调、构造器或全局 `nodeuuid` 的用例使用 `test`。
每项创建独立浏览器上下文，存储、DOM、全局变量和监听器不从上一项继承；未处理的页面异常也会判失败。
自定义函数可以返回 Promise，但不能使用 Node.js 外层闭包变量。需要等待的异步副作用应在函数内等待完成再返回布尔值。
