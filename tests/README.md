# translate.js 自动化测试

本目录集中保存 translate.js 的测试入口、按方法组织的测试模块、完整流程测试及测试工具。
目标是让开发者修改代码后运行同一个入口，及时发现参数处理错误、功能回退和浏览器异常。
测试应逐步覆盖每个方法的正常行为、边界、异常和相关参数组合；不能以少量正常示例代替详细验证。

## 已确定的目录和命名

```text
tests/
├─ README.md                       本文：目标、组织方式、待商定事项和进度
├─ test-translate.js.bat            Windows 双击运行入口
├─ start.js                        准备依赖、选择浏览器、运行和汇总结果
├─ playwright.config.js            测试发现与浏览器配置
├─ package.json / package-lock.json 锁定测试依赖
├─ modules/                        按方法命名，文件平铺，不建立多层方法子目录
│  ├─ storage.get.js                对应 translate.storage.get()
│  ├─ storage.set.js                对应 translate.storage.set()
│  ├─ storage.browser.memory.get.js 对应 translate.storage.browser.memory.get()
│  ├─ util.textReplace.js           对应 translate.util.textReplace()
│  └─ ...                           方法文件是后续示例，此次不创建空壳测试
├─ scenarios/                      暂存现有跨方法的浏览器流程测试
├─ fixtures/                       本地测试页面及模拟接口服务
├─ helpers/                        多个测试确实需要时才提取公共辅助代码
├─ report/                         当前结果及保留的历史验证资料
└─ test-results/                   自动生成的失败截图、跟踪等文件
```

- 方法文件名省略共同的 `translate.` 前缀，其余路径与源码方法一致，例如 `element.iframe.execute.js`。
- `modules/` 保持平铺；不再按 `storage/browser/memory/` 等路径建立层层子目录。
- 一个方法对应一个测试模块文件；每种参数组合、边界或异常情况是独立测试，能够单独定位失败。
- 允许在一个方法文件内使用参数表生成多个独立测试，避免重复代码；具体格式仍需商定。
- 多方法协作的完整流程放在 `scenarios/`，保留对真实页面最终行为的验证。
- 测试入口只发现 `modules/` 和 `scenarios/` 的 `.js` 文件；辅助程序和模拟服务不作为测试执行。
- 暂不为了统一外观拆分原有聚合场景；应先确认方法模块规范，再逐步迁移和核对。

## 单个方法测试需要记录的内容

以下是覆盖要求，不是已经定稿的 JavaScript 数据结构或模板。

1. 明确被测方法、参数及预期行为。每项说明它要证明什么，失败时能定位具体方法和参数组合。
2. 覆盖正常值、可选参数省略、边界值、特殊字符、适用的数据类型及相关参数间的组合。
3. 根据方法约定检查错误类型、返回值和副作用，例如是否修改输入数组、DOM、存储或内部状态。
4. 需要时验证连续调用、状态变化前后、失败后的行为以及功能之间的协作。
5. 预期结果来自明确的功能约定或独立核对，不能照着当前实现计算答案，再证明实现与自己一致。
6. 未定义的输入行为先记录并与维护者确认，不能自行规定必须成功、必须返回空值或必须抛错。
7. 每项独立报告结果，测试之间不依赖上一项留下的状态。

输入集合可能无限，有限测试不能证明任意输入下绝对没有 bug。为避免漏项，需要维护可核对的覆盖清单，
逐项记录方法、参数、已覆盖情况、待补充情况和待确认的行为。不能把“测试通过”写成“全部方法已覆盖”。

## 模块内部规范：待共同商定

目录和文件名已经确定；以下内容需要在编写第一批方法模块前逐项讨论，确认后再补正式规范及示例：

- 独立测试的编号、中文名称、说明和源码方法之间如何对应。
- 参数表、预期返回值、预期异常及副作用断言采用怎样的表达方式。
- 公共准备/清理、状态隔离以及方法测试与浏览器环境之间的边界。
- 无参、缺参、`undefined`、`null`、空值和不同类型怎样分类，以及哪些属于未定义行为。
- 参数组合如何覆盖，有哪些必须逐项枚举，何时采用组合策略，如何记录未覆盖项。
- 原验证页条目如何保留来源和编号，重复条目及预期冲突如何处理。
- 测试所需环境、超时、异步完成条件，以及失败信息应包含哪些内容。
- 已知问题、临时跳过、已修复回归的登记及退出机制。
- 模块如何自动发现，以及维护方法覆盖清单，及时发现遗漏文件或没有用例的方法。

规范确认前，不建立一套复杂的自定义测试框架，也不擅自固定用例对象格式。

## 运行方式与环境

迁移完成后，Windows 直接双击 `tests/test-translate.js.bat`；AI 或脚本可在仓库根目录执行：

```bat
tests\test-translate.js.bat --no-pause
```

需要 Windows 10/11、Node.js 20 或更新版本和 npm。缺失的锁定依赖由启动器安装；优先使用配套 Chromium，
也会尝试可运行的本机 Playwright 缓存，没有可用浏览器时下载 Headless Shell。
首次准备需要网络；本地 `127.0.0.1:8123`、`8124` 端口须空闲，服务由工具自动启停。
测试使用本地页面及模拟翻译响应，不依赖真实翻译服务的速度和稳定性。

同一批测试分别检查实际磁盘上的 `translate.js/translate.js` 和 `translate.js/translate.min.js`。
工具不自动生成压缩文件，两份文件可能处于不同修复进度，应分别看结果。
迁移只改变测试组织和路径，不修改运行库或版本号。

默认运行显示正常通过、已知失败、跳过和意外失败。退出码 0 表示没有意外失败，非 0 表示测试或环境准备失败。
已知失败不代表功能正常；严格模式 `--strict` 取消这类豁免，现存问题会让命令失败。
当前还需收紧部分已修复场景保留的旧豁免，否则同签名的旧问题复发可能再次被记为已知失败。
这一判定修正列为独立后续任务，不混入此次目录迁移。

## 修改和维护原则

- 追踪问题根源，以最少且清楚的改动解决目标；避免用新增机制掩盖旧问题或堆积辅助层。
- 按可独立验证的改动拆分提交，使用详细中文提交说明，每次完成后提交并推送。
- 相互依赖的文件移动与路径修正属于同一次完整迁移，避免提交后入口暂时不能运行。
- 有不确定且存在多个处理方向的地方，先列出选项让维护者选择，不自行替代决定。
- 代码注释说明用途、约束和容易误解的边界；审查 diff 时保留前后至少各五行上下文。
- 修改前记录基线，修改后运行相同测试，核对原有通过项、已知失败特征、跳过项及测试数量。
- 新发现问题单独记录和讨论，不为让本次测试变绿而放宽断言或顺便扩大运行库改动。
- 已修复问题应成为必须通过的回归测试，不能长期通过“已知失败”隐藏复发。
